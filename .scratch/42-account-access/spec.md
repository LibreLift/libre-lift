# Task: Complete application User integration for account access

Published: https://github.com/open-source-fitness/open-fit/issues/107

**Goal**: Users access their account using the application-owned account name and recover from failed account loading without repeating successful code verification.

**Context**: Completion specification for [#42](https://github.com/open-source-fitness/open-fit/issues/42), part of #40 and M1: Runnable Demo. PR #99 delivered the email-code UI using Auth metadata. Completed #102 now supplies the application User schema. This specification covers the remaining work; it preserves #42's existing scope and In progress execution status.

Implementation: agent for application changes and local verification; human for hosted configuration and supported-device acceptance audit.

**Acceptance criteria**:

- [ ] Successful verification loads the authenticated account's application User; an existing User supplies the displayed account name regardless of Auth metadata.
- [ ] A failed User lookup keeps training gated and exposes Retry loading account, retrying only that lookup with the verified session.
- [ ] Only a successful lookup with no User requires name onboarding; verification and reads do not create a User.
- [ ] Submitting a valid onboarding name creates the authenticated account's User; Account name editing updates that User without changing its identity or sign-in email.
- [ ] Pending operations prevent conflicting actions; recoverable failures preserve useful input and offer retry.
- [ ] Router tests and actual local Supabase checks establish correct storage, recovery, onboarding, editing, and returning access.
- [ ] Documentation matches the application User contract, required checks pass, and hosted/device audit results are recorded before completion is claimed.

## Problem Statement

Account access currently stores account names in Auth metadata. The agreed application data model instead stores the name on an application User sharing the Auth account's UUID. Consequently, the app can display a metadata name while no application User exists, or ignore an existing User's authoritative name. Training persistence cannot rely on this incomplete onboarding integration.

Adding the required User lookup also introduces a recovery boundary: a code can verify successfully before account data fails to load. Repeating a consumed code is not a usable recovery path.

## Solution

After email-code verification, load the application User. Existing Users enter Templates with their stored name; accounts without a User supply a name first. If loading fails, keep the user in an account-loading error state with Retry loading account. That action uses the already verified authentication session to retry the User lookup. Account name creation and editing persist to the same application User contract.

## Implementation Decisions

- Preserve email OTP as the sole access method, its existing validation, six-digit codes, ten-minute expiry, sixty-second resend cooldown, and abandoned-attempt behavior.
- Use the existing injected asynchronous service and MVVM boundaries. Views consume application account state rather than SDK types or tokens.
- Separate successful authentication from resolution of application account data. Retain verified authentication in memory while the User lookup is pending or failed; only completed User resolution can select Templates or name onboarding.
- Retry loading account repeats only the authenticated User lookup. Show progress, prevent duplicate/conflicting operations, retain retry after repeated failure, and keep appearance Settings reachable. An error is never evidence that a User is absent.
- Read the application-owned User by the authenticated account UUID using the ordinary authenticated client and existing owner policies. Account names in Auth metadata are nonauthoritative.
- The existing User table and its constraints, grants, and RLS are supplied by #102. No schema changes, Auth triggers, privileged client, or automatic User creation on verification/read are required.
- A successful empty lookup requires explicit name onboarding even if Auth metadata contains a name. Submitting a nonblank trimmed name creates the User. Name editing updates the existing User's account name only.
- Keep Account identity and email supplied by Auth and its name supplied by the application User. Names are editable, nonunique display names, not sign-in identifiers.
- Preserve name drafts on failure, maintain correction/retry and Cancel behavior, and reconcile ambiguous creation outcomes against the existing User rather than creating a second identity or silently treating an error as success.
- Preserve route protection, Back behavior, light/dark/system appearance, native accessibility, and existing training functionality behind the gate.
- Update account-access setup and verification documentation to describe application User storage and recovery. Retain the already recorded human-facing recovery decision; this reversible UI decision needs no additional ADR or glossary term.
