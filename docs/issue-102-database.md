## Problem Statement

Users need account names and workout templates to survive app reloads, development builds, updates, and reinstalls. The repository currently has Supabase development infrastructure but no application tables or database access policies. Training data is held by an injected in-memory service. Account-access work also needs an application-owned place to store the account name rather than using Auth metadata.

Issue #45 cannot integrate persistent templates safely until table structure, ownership, snapshots, and constraints are agreed and reproducible. The original #102 criteria combined database infrastructure with app integration and authentication-session restoration; those responsibilities belong to different tasks.

## Solution

Build the M1 database foundation in #102, with secure application User and template storage that later app integrations can use. A verified person supplies an account name to establish their application User. Saved templates retain ordered exercises, complete exercise descriptions, and independent set targets under that User's ownership.

Issue #42 integrates account-name onboarding and editing; #45 integrates template operations and the app's production persistence service; #43 restores valid stored authentication and handles sign-out. Together those integrations allow saved data to remain available across app lifecycles when using the same backend. This infrastructure issue alone does not deliver those app flows.

## User Stories

1. As a verified user, I want my chosen account name stored with my application User, so that my account retains its display name.
2. As a verified user without an application User, I want to supply a name before entering training screens, so that onboarding creates a complete User record.
3. As a returning user, I want my existing application User and name loaded, so that I do not create another record on each sign-in.
4. As a user, I want to edit my account name without changing my sign-in identity, so that I can change how my account is displayed.
5. As a user, I want my account name to be independent of other users' choices, so that it need not be a unique handle.
6. As a user, I want saved templates associated with my stable account identity, so that later app integrations can reload my training data after a restart or update.
7. As a user who reinstalls the app, I want my saved templates retained in the same backend, so that signing in again can restore access to them.
8. As a user, I want separate templates to have independent identities even when their names match, so that duplicate names do not merge my plans.
9. As a user, I want saved template titles and optional descriptions preserved, so that reopened templates retain their meaning.
10. As a user, I want my exercises to retain their order, so that the saved template reflects my intended sequence.
11. As a user, I want moving an exercise to preserve its identity and targets, so that reordering does not mix up set data.
12. As a user, I want repeated placements of the same catalog exercise to remain independent, so that each can have different planned sets.
13. As a user, I want a saved movement to retain its catalog identity, so that its source movement remains identifiable.
14. As a user, I want saved exercise names, muscles, equipment, and available supplementary details preserved, so that upstream catalog changes do not rewrite my template.
15. As a user, I want saved exercise detail available without another catalog request, so that viewing my plan does not depend on the live catalog.
16. As a user, I want each placement's numbered sets and targets preserved, so that later reads return the repetitions and weights I saved.
17. As a user, I want zero and decimal pound targets supported, so that valid fixed-weight plans can be represented accurately.
18. As a user, I want invalid target values rejected, so that stored plans do not contain unusable repetitions or weights.
19. As a user, I want my account name and templates private to my account, so that other users cannot read them.
20. As a user, I want other accounts unable to modify, delete, or attach records to my templates, so that ownership protects the whole saved plan.
21. As a user, I want anonymous requests denied access to personal data, so that signing out does not leave database access open.
22. As a user, I want deleting a template to remove its placements and sets, so that abandoned template data is not retained.
23. As a user whose Auth account is administratively deleted, I want its application User and owned templates removed, so that orphaned personal records do not remain.
24. As a contributor, I want committed migrations to reproduce the schema locally, so that I can build integrations without hosted administrative access.
25. As a contributor, I want actual database tests for two users and anonymous access, so that policy mistakes are detected before integration.
26. As a maintainer, I want schema changes tested against existing records, so that extending the database does not discard user data.
27. As a maintainer, I want explicit reviewed deployment instructions without automatic sample seeding, so that deploying the schema does not populate users' accounts with demonstration data.

## Implementation Decisions

- Create only the M1 application schema: User, workout template, template exercise, and template set. M2 session/history, personal-maximum, and percentage-target tables or extensions remain in their existing tasks and are added through later migrations.
- Supabase Auth remains responsible for credentials and authentication sessions. The application User has the same UUID as its Auth account, enforced by a relationship to the managed Auth account's primary identity. Do not alter the managed Auth schema to add application fields.
- Store the required nonblank editable account name on the application User. It is a nonunique display name, not a username or sign-in identifier. Training ownership references the application User, rather than duplicating account names or treating names as keys.
- Account reads after successful email verification return the existing User or indicate onboarding is required. Reads do not create an incomplete User. Submitting a valid account name creates the User; subsequent reads reuse that identity. Name editing updates the existing record. Failed submissions preserve input for retry in #42's UI. The name in Auth metadata is not the application's authoritative source.
- #102 supplies the User schema, constraints, and access policies. #42 supplies account-data reads, creation on name submission, name editing, and onboarding integration. Update #42's existing metadata-based implementation accordingly; no Auth trigger creates a blank application User.
- Templates store their owner, UUID identity, title, optional description, and creation timestamp. Duplicate template names are valid. Creation timestamps support stable listing order; #45 implements the listing contract.
- Template-exercise placements have UUID identities independent of their numeric positions. A placement retains its parent template and namespaced catalog identity. Repeated placements of the same catalog exercise are valid. #45 translates temporary draft identities when persisting new records; reordering preserves saved identities.
- Each placement stores a complete descriptive JSON snapshot of the existing catalog model: name, separate primary/secondary muscles, equipment, and available images, instructions, and translations. Preserve distinctions such as unspecified equipment versus explicit no equipment. Keep relationships, identity, ordering, and target sets relational. Do not import a shared catalog table or resolve saved descriptions through live catalog joins.
- Template sets belong to a placement and use numbered identities within that placement. Store positive integer target reps and finite nonnegative decimal fixed target weights in pounds. Zero weight is valid; percentages and unit conversion are deferred.
- Enforce valid relationships, nonblank names, unique placement positions within a template, and unique set numbers within a placement. Validate numeric ordering values consistently with numbered sets and positions. #45 owns whole-template validation and atomic saves: at least one exercise, at least one set per exercise, and consecutive ordering. Do not reject temporary intermediate structure required during a multirow transaction.
- Add explicit grants and RLS rather than relying on automatic table exposure. Anonymous requests cannot access application User or template data. Authenticated requests can access only their own User and template aggregate. Child-record policies must protect inserts, updates, reads, and deletes, including attempts to attach records to another user's template or placement.
- Users cannot change their identity or transfer ownership. Future backend operations execute in the requesting account's authenticated context so RLS applies; privileged service credentials are not the routine application data-access path.
- Deleting a template cascades to its placements and sets. Deleting an Auth account cascades to its application User and owned templates. This specifies database behavior and does not add an account-deletion UI.
- Version-controlled migrations are authoritative. Use later migrations to extend populated deployments; do not reset hosted data or rewrite shared migration history. No automatic creation of sample templates or user seed data.
- #102 delivers locally verified schema and deployment instructions. Shared hosted application follows the existing manual maintainer process after review; committing migrations does not deploy them.
- Transfer template schema migrations, database constraints, grants, and ownership policies from #45 to #102. #45 retains TypeScript service contracts, HTTP handlers/data access, payload validation, atomic template CRUD, production app integration, and end-to-end persistence checks. Temporary drafts and controlled test doubles remain valid; removal of every in-memory object is not an acceptance criterion.
- #43 retains valid-session restoration, sign-out, invalid/revoked authentication handling, and account-state cleanup. Explicit sign-out or app reinstall requires another OTP. No application-imposed authentication lifetime or inactivity timeout is introduced here.

## Testing Decisions

- The maintainer approved the real local Supabase database as the primary and highest applicable seam for this infrastructure task. Test observable stored data, allowed/denied operations, and relational behavior; avoid assertions about SQL formatting, internal policy names, or helper implementation.
- Test the application User and template aggregate under anonymous access and two authenticated identities. Administrative setup may provision test Auth accounts; permission assertions must run as the appropriate nonprivileged actor.
- Verify User creation with a name, existing-name reads and editing, identity matching, duplicate-name allowance, and invalid-name rejection. Authentication-only presence must not automatically create an application User.
- Round-trip template title/description, creation timestamp, repeated exercise placements, independent UUIDs, saved descriptive JSON, ordered positions, numbered sets, zero/decimal pound weights, and positive reps. Reordering must preserve identity and each placement's targets.
- Verify anonymous rejection and cross-user reads, updates, inserts, deletes, foreign-parent attachment, identity changes, and ownership-transfer attempts for all relevant relationships. Include permitted operations to ensure policies do not merely deny everything.
- Verify invalid numeric values, duplicate positions/set numbers, and broken relationships are rejected. Do not require per-row writes to enforce the complete-template cardinality rules owned by #45.
- Verify template-to-child deletion cascades and administrative Auth-account deletion cascades without deleting another user's data.
- Verify a clean local rebuild and a migration application against representative preexisting Auth/application records where applicable; preserve sentinel records through incremental migration application. The initial schema can be applied to a database with existing Auth accounts without inventing application User rows or names. Do not fabricate unused M2 migrations solely for a test.
- There is no existing database-test suite in the repository. Existing service tests provide behavioral prior art for independent placements, snapshots, ordering, invalid targets, and atomic failure; migration documentation provides the clean-rebuild workflow. Select a small database-test harness consistent with the approved seam and document its checked-in commands during implementation.
- UI onboarding, request error/retry handling, and authentication-session restoration tests remain with #42/#43. Whole-template CRUD and app-restart persistence tests remain with #45. Existing Jest/TypeScript checks remain the relevant regression checks if implementation changes their inputs.
