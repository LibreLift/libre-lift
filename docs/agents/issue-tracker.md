# Issue tracker: GitHub

Issues and specs live in [LibreLift/libre-lift](https://github.com/LibreLift/libre-lift/issues).
Use the `gh` CLI with `--repo LibreLift/libre-lift` for issue operations. The local
origin still uses the former `LibreLift/expo_suite` name, which GitHub redirects.

Read [project management](../project-mgmt.md) before tracker changes. Use its
issue templates, milestone rules, assignment process, and definition of done.

## Issue operations

- Read: `gh issue view NUMBER --repo LibreLift/libre-lift --comments`.
- List: `gh issue list --repo LibreLift/libre-lift --state open --json number,title,labels,assignees`.
- Create: `gh issue create --repo LibreLift/libre-lift --title TITLE --body-file FILE --label LABEL`.
- Comment: `gh issue comment NUMBER --repo LibreLift/libre-lift --body-file FILE`.
- Labels: `gh issue edit NUMBER --repo LibreLift/libre-lift --add-label LABEL --remove-label LABEL`.
- Close: `gh issue close NUMBER --repo LibreLift/libre-lift --reason REASON`;
  use `completed` for delivered work or `not planned` for declined/superseded work.

Write multiline bodies to a file and pass `--body-file`. Use the matching
`.github/ISSUE_TEMPLATE/` structure. During triage, every published issue or comment
must start with `> *This was generated by AI during triage.*`.

## Project board

The board is [LibreLift MVP, organization project 1](https://github.com/orgs/LibreLift/projects/1).
Issue labels and board fields are separate. Use the mapping in
[triage labels](./triage-labels.md) for readiness and execution roles.

Inspect current fields with `gh project field-list 1 --owner LibreLift --format json`
and items with `gh project item-list 1 --owner LibreLift --format json`. Resolve
current project, field, item, and option IDs before a board edit; use
`gh project item-edit` for field changes. Check view filters before treating an
item as absent. Reuse the existing Status and Task Size fields and their options.

Project reads require the `read:project` token scope; writes require `project`.
If CLI access is unavailable, the public board can be inspected read-only. Report
blocked board edits and leave them pending rather than claiming synchronization.

## Dependencies and claiming work

Use native GitHub sub-issues for epics and native issue dependencies for blockers.
If unavailable, record `Part of #NUMBER` and `Blocked by: #NUMBER` links in the
issue body. A blocked task is not Ready. Apply `planned work` only with maintainer
authorization; follow the repository's assignment process before claiming work.

When a skill says to publish a spec or fetch a ticket, create or read a GitHub
issue in this repository. Follow repository label mappings instead of creating
labels named after a skill or its internal roles.
