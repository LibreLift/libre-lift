## Problem Statement

The template editor already lets a user create and maintain complete workout templates, but its production service stores them only in memory and restores demonstration templates on reload. Users lose saved work when the app restarts and cannot recover it after an update or reinstall. Database tables alone do not connect that workflow to durable, account-private storage.

Network failures also make saving ambiguous: the database may commit even when the app never receives the response. A reliable persistence integration must preserve the draft, allow a safe retry, and prevent partially stored templates or accidental duplicate creation.

## Solution

Replace the production template operations with authenticated backend persistence while preserving the existing editor. A successful Save stores the entire template together. Reopening restores its saved exercise descriptions, order, and targets without fetching the live catalog. Saved templates remain available to the same account on the same backend after restarts, updates, and reinstall followed by email OTP access.

New accounts begin with no saved templates. Unsaved drafts remain temporary. Failures leave the draft available for correction or retry while authentication remains valid. The Workouts tab continues to demonstrate sample history, clearly labeled as sample data until session persistence arrives in #47.

## Implementation Decisions

- Preserve MVVM and the injected asynchronous workout-service contract. Use the account-scoped service factory introduced by #118 as the production composition seam; retain controlled in-memory services for tests. Template operations use persistence, while session reads continue to return clearly labeled sample history. Do not silently fall back to sample templates when configuration or requests fail.
- Share one lazily configured Supabase client/runtime between authentication and template persistence. The factory's Account argument establishes service lifetime, not authorization. Obtain current credentials for each request; do not capture an access token when constructing the service. Preserve #118's same-account refresh behavior and account-generation cleanup.
- Keep the design's service → authenticated HTTP handler/Edge Function → data access → database boundaries. HTTP handlers validate the request and authentication, data access maps the aggregate, and a narrow transactional database function performs atomic writes with invoker rights under the requesting user's authenticated context. Never use privileged service credentials for routine template operations. Add this function and any necessary retry metadata through new migrations rather than editing #102's shared migrations. Existing ownership constraints, grants, and RLS remain authoritative; new function access and metadata must be explicitly owner-scoped.
- Provide typed request/response and service contracts for list, detail, creation, whole-template update, and deletion. Validate untrusted JSON at runtime, including nested snapshots and numbers; TypeScript types alone are insufficient. Keep the existing metadata-update method coherent with whole-template persistence rather than bypassing validation. Return canonical saved aggregates after mutations, with useful categories for validation, authentication, missing records, and retryable request failure; do not expose backend internals or another owner's existence.
- Saved templates and placements use UUIDs. Translate temporary draft placement identities when creating records, including newly added placements on an existing template. Preserve surviving placement UUIDs through edits/reordering, independent of catalog identity. Reject duplicate, foreign, or unrelated saved placement identities rather than reparenting them. Server operations determine ownership from authenticated context, never a trusted client-supplied owner.
- Store immutable creation timestamps and list templates in ascending creation-time order with UUID as a deterministic tie-breaker. New templates append under normal creation order; editing does not change creation time or list position. Read placements and sets in explicit one-based order. Ensure backend row limits cannot silently truncate a list or aggregate; the service's complete-list contract does not require a new paginated UI.
- Preserve complete descriptive snapshots from the shared catalog model: name, distinct primary and secondary muscles, equipment, and available image, instruction, and translation content. Preserve catalog identity relationally and maintain existing distinctions for missing optional data. Do not join to or fetch the live catalog when opening saved detail. Persisting image references preserves the existing loading/unavailable behavior; this feature does not download or guarantee external image availability.
- Keep template-exercise positions separate from UUID identities. Template sets retain their one-based set numbers, positive integer reps, and finite nonnegative fixed target weights in pounds, including zero and decimals. Preserve existing trimmed nonblank title and description behavior; duplicate titles are valid. Save requires at least one exercise, at least one valid set per placement, and consecutive final ordering. Incomplete drafts remain permitted before Save.
- Validate the complete aggregate and commit all metadata, membership, snapshots, ordering, and sets together. Defer ordering uniqueness within the transaction when necessary, validating the final state before commit. Failure rolls back both aggregate changes and any successful-save retry record. Deletion uses existing cascades. Database row policies are not a substitute for the whole-template rules at the save boundary.
- Assign a stable template UUID to a creation draft's persistence operation and retain its temporary-to-saved identity mapping across retries while the draft/account lifetime remains active. Associate each distinct save attempt with an owner-scoped operation identity and its content. The same operation and unchanged content recover the original committed result rather than writing again. Reject reuse of an operation identity for different content. Changing the retained draft creates a new operation against that same template identity, whether or not the earlier response arrived. Do not deduplicate by title or catalog content.
- Make successful-save recognition durable on the server and atomic with the save. Replays must not overwrite later distinct saves, reinsert deleted templates, reveal foreign records, or cross account boundaries. Check current ownership/existence before returning a historical result after deletion. A definitive failed transaction does not count as a committed operation and remains retryable. Client retry information is temporary; persisting unfinished drafts across restart is out of scope. The schema and storage representation of retry recognition are implementation choices subject to these observable guarantees.
- Serialize concurrent writes to the same template so each distinct save is a whole-template transaction. The last committed distinct save wins. Do not add version-conflict UI, merging, or live cross-device synchronization. Replaying an already committed operation is not a new save. Distinguish retrying an uncertain creation from an update: updates cannot create records, and an absent committed creation cannot be resurrected by replay.
- Owner-scoped missing/inaccessible detail reads return the existing missing-template state. Missing/inaccessible updates return the same non-disclosing missing-record failure. Deleting a valid but absent or inaccessible ID is a successful no-op; deleting a foreign ID never changes that owner's data. Invalid identifiers remain validation errors. This intentionally supersedes the in-memory service's missing-delete error behavior for the persistent contract.
- Preserve existing loading/retry, Save/Cancel, discard guards, tab-retained drafts, pending locks, saved-detail navigation, and summary refreshes. On ordinary failed writes, keep the whole draft editable and retryable. Treat a committed mutation followed by a failed refresh as a read failure, without falsely reporting that the saved transaction rolled back. The lost-response rules cover transport failures whose commit result is unknown.
- Add a narrow notification bridge from definitive protected-request authentication rejection to #118's existing account recovery. Refreshable expiry uses the shared auth runtime; a generic 403, validation failure, unavailable account record, or transport error is not evidence that authentication ended. Routine refresh preserves services/drafts; definitive auth loss, sign-out, or account change clears account-owned state and ignores late results. Do not automatically replay a previous account's pending write under a newly signed-in account.
- Do not seed or migrate the former in-memory sample templates into accounts. Keep session-history fixtures independent of persistent template identities and label them visibly as sample history. This label is the only necessary change to the Workouts experience before #47.

## Testing Decisions

- The maintainer approved two complementary existing integration boundaries: router-level behavior tests and the real production service through HTTP/Edge Function to disposable local Supabase. Prefer these high boundaries to new hook-by-hook or SQL-implementation tests. A good test asserts visible behavior or saved outcomes, not component layout structure, incidental SDK call sequences, SQL text, helper names, or policy names.
- Reuse the existing root injection/account-scoped factory, real Views/ViewModels/navigation, and controlled service wrappers for loading, pending, validation, failure, retry, cancellation, and account-lifecycle scenarios. Existing template builder/editor/navigation and auth-navigation suites provide prior art. Keep focused service-contract checks only where they expose distinct identity/snapshot outcomes efficiently.
- Run actual production template service requests through the local endpoint and database using nonprivileged authenticated clients. Provision two test accounts and application Users administratively only for setup, following the existing disposable authentication-check approach. Permission assertions must use anonymous or the relevant user's credentials, never an administrative bypass.
- Round-trip creation, read/list, whole-template edits, addition/removal, reordering, deletion, duplicate titles, stable list order, UUID stability, zero/decimal weights, independent repeated placements, and all optional snapshot content. Saved detail must not request catalog JSON. Cover empty accounts, missing records, invalid payloads, and complete results when backend row limits would otherwise truncate them.
- Prove rollback with a failure during a multirow write after some work has begun, not only a payload rejected before writing. Confirm the previously saved aggregate and successful-operation recognition remain unchanged. Verify two actual saves cannot interleave into a mixed aggregate.
- Simulate a committed save whose response is lost, then retry unchanged content and confirm one template and the original result. Edit the retained draft and save again to the same template identity; replay the earlier operation and confirm it cannot undo the later state. Reject the same operation identity with changed content. Cover independent devices' last-committed-save rule, delete-response loss, update-after-delete, and creation replay after deletion without resurrection.
- Verify actual anonymous and cross-user list/detail/mutation requests, guessed template/placement IDs, foreign-parent attachment, and operation-identity reuse cannot disclose or change another user's aggregate or replay data. Include successful owner operations so a deny-everything implementation cannot pass. Reuse #102's database suite for its existing row-policy/constraint/cascade coverage; add targeted database checks for new functions or retry metadata as needed.
- Verify ordinary failed writes preserve the draft, read failures do not appear as empty data, pending controls prevent duplicate taps, and missing/idempotent-delete outcomes match the contract. Verify a committed save plus failed subsequent read offers read recovery rather than an incorrect rollback claim.
- Verify token refresh keeps the editor/draft intact, definitive request auth loss enters recovery, connection/permission failures do not spuriously sign out, and account changes/sign-out discard old drafts and late responses. Reuse #118's lifecycle tests rather than reimplementing its restoration behavior.
- Recreate the app/service with the same backend and account, restore authentication or sign in again, and assert saved templates remain. Temporary drafts need not survive. Separately perform supported-device review for app restart/update and reinstall followed by OTP access to the same account; automated service recreation alone does not establish every native lifecycle claim.
- Verify the Workouts tab labels sample history clearly and template edits/deletion leave its independent data unchanged. Retain existing native drag/accessibility, themes, keyboard, and increased-text-size review where persistence integration affects them.
- During implementation run the checked-in TypeScript/Jest checks, database checks for additive migrations, and a documented repeatable local full-stack template check. Extend the disposable verification approach to serve required Edge Functions without resetting or modifying a shared/hosted backend. Run relevant Expo/native checks for changed app composition. Record which checks actually ran and which require reviewer/device follow-up.
