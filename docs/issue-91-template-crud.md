## Problem Statement

Users can browse sample workout templates and edit their names and descriptions, but cannot build and maintain complete templates. They need to choose catalog exercises, define planned sets, organize exercise order, and save or delete templates through a usable app flow before database integration is available.

## Solution

Provide complete template CRUD through Templates. Users select catalog exercises, enter fixed target weights and repetitions for each set, and drag exercises into order. Explicit Save commits the entire draft to an in-memory service. Saved changes survive navigation and screen reopening during the running app session. Restarting or reloading restores the two bundled samples.

## Implementation Decisions

- Further November 16 refinement: saved templates also use two screen types. The saved overview lists exercise names and short set-count summaries; opening a placement shows its saved image and compact read-only target rows using the same layout as the set editor. Resolve placements by their own identity, not by catalog identity, and use saved snapshots without a catalog request. Missing imagery has an unavailable placeholder. The editing overview's button text is Sets, inline with the exercise title and trash control, with a contextual accessibility label.

- November 16 UI refinement: split editing into two screen types. The template overview edits metadata, exercise membership/count, and order using compact placement summaries. A separate exercise editor manages only that placement's sets and targets, with each set in a single row: Set N: [reps] × [weight] lb. Back/Done returns to the overview preserving the shared draft; Save/Cancel on the overview applies to the entire template. This refines presentation without adding per-exercise persistence.

- Extend existing MVVM: Views render ViewModels, which use the injected asynchronous WorkoutService. The root owns the in-memory instance. Saved state must not live in route-local fixtures or be accessed directly by Views.
- Extend the template contract with create, whole-template update, and delete alongside list/read; preserve session reads. Existing metadata editing must remain coherent with the full editor and share saved state and validation rules.
- Save the complete draft atomically. Invalid or failed writes leave saved state unchanged. The service assigns template IDs; existing template IDs and surviving placement IDs stay stable through edits/reordering. Repeated catalog exercises receive independent placement identities.
- Incoming drafts, stored records, and returned objects must not permit caller mutation or unsaved edits to change stored templates. Preserve nested exercise snapshots, catalog identity, and independent workout history under existing ADRs.
- Saving requires a trimmed nonblank name, at least one template exercise, and at least one set per exercise. Description is optional and retains existing text behavior. Duplicate names are allowed. Incomplete drafts, including exercises without sets, are permitted while editing.
- Fixed weights use pounds and must be finite and nonnegative, including decimals and zero. Reps must be positive integers. Blank numeric inputs are incomplete, never silently zero. Enforce validation at the service boundary and show useful correction feedback in the editor.
- A new exercise starts with one set with blank targets. Add set appends a copy of the preceding set's values; when no sets remain, it appends a blank set. Each set has independent inputs and Remove. Display consecutive set numbers; preserve their order.
- Add exercise opens the existing searchable catalog in builder context. Users may inspect detail and explicitly add one exercise, appending it and returning to the draft. Back without adding preserves the draft. Retain standalone browsing without unintended draft mutations.
- Catalog loading/failure leaves the draft intact. Users can return and reopen using existing catalog loading behavior. No new catalog retry or caching mechanism is required.
- Include drag-and-drop for template exercises. Show a traditional three-horizontal-line handle on one side only during creation/editing. Long-press the handle to drag, scroll while dragging, and provide accessible Move up/Move down alternatives. Moving a placement retains its sets/values. Sets are not draggable.
- One draft includes metadata, exercises, targets, and order. Save/Cancel applies to all of it. Tab changes preserve the draft. Back/swipe with unsaved changes prompts Discard changes/Keep editing. Internal catalog navigation must not be treated as abandoning the draft.
- Cancel creation returns to the list without creating a record. Cancel editing restores read-only saved detail. Successful create/update opens read-only detail and refreshes list/detail and counts. New templates append; edits retain list position.
- Show pending save state; disable conflicting fields/actions, Back/swipe, and tab navigation until settled, consistent with existing guards. Prevent duplicate submissions. Failure preserves the whole draft for retry and restores navigation and editing.
- Delete from read-only detail after confirmation naming the template. Success returns to the refreshed list. Failure retains visible detail and retry; prevent overlapping deletion actions. The empty state offers Create.
- Missing-record reads retain existing missing-detail behavior. Missing-record updates/deletes report useful errors and never silently recreate records.
- Initialize each fresh service instance with the two samples. Saved changes survive navigation/reopening. Restart/reload discards saves and unfinished drafts and restores samples. Do not write training data to local storage or a database.
- Preserve existing appearance behavior and support accessible labels/actions, keyboard use, and increased text size on supported mobile platforms.

## Testing Decisions

- Approved primary seam: existing router-level tests with real Views, ViewModels, navigation, and the in-memory service through root dependency injection. No new testing abstraction is needed.
- Test externally visible behavior and service outcomes, not component structure, hook internals, or incidental call ordering. Existing template navigation, editor, and pending-save/error/retry tests provide prior art.
- Cover creation, reopening, full edits, catalog selection/cancellation/loading/failure, repeated placements, independent targets, set addition/removal, validation, order, counts, cancellation, tab preservation, Back/swipe guards, pending controls, save failure/retry, deletion confirmation/failure, empty/missing states, and read-only handle visibility.
- Supplement with focused public service-contract tests, following existing workout-service tests, for rejected-write atomicity, missing-record writes, stable IDs, duplicate names, ordering, snapshot isolation, independent placements, unchanged history, and fresh-instance reset. Avoid duplicating every route outcome with hook tests.
- Inject controlled asynchronous workout-service wrappers to verify pending/failure/retry behavior, despite memory backing. Use the existing injectable catalog service for controlled catalog results.
- Automatically verify reordered results and accessible Move up/Move down actions. On a supported device or simulator verify actual native long-press dragging, three-line handle visibility, scrolling, placement targeting, and preserved set values. A simulated reorder callback alone does not establish drag usability.
- During implementation run the checked-in TypeScript and Jest commands, applicable native dependency/bundling checks, and supported-device review. Physical iPhone with Expo Go is the first review target; Android remains supported. Check both themes, keyboard behavior, and increased text size.
