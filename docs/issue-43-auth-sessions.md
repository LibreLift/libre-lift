## Problem Statement

OpenFit stores Supabase credentials on the device but does not restore them into application state when the app launches. Returning users must repeat account access, and the app does not yet respond to session lifecycle changes or provide sign-out.

Training services, cached reads, and unfinished work can outlive protected routes. Simply returning to email entry would therefore leave the previous account's state available in memory. Users need reliable returning access and a clear boundary that prevents one account's state from appearing under another account.

## Solution

Restore usable stored authentication behind a loading gate, load the application User, and enter the app only after any required account-name onboarding. Keep sessions renewable without an application-imposed maximum lifetime or inactivity timeout.

Routine same-account token refresh preserves ongoing work. When authentication becomes unusable, gate training. Temporary failures offer recovery without erasing stored authentication; successful recovery starts with a clean load and discards drafts and navigation. Definitively invalid authentication clears account-specific state and returns to email access.

Provide device-local sign-out. Clear account-specific services, caches, edits, drafts, and navigation when authentication ends or the account changes, and prevent late responses from repopulating them. Preserve device appearance preferences and saved backend data.

## Implementation Decisions

- Extend the existing injected asynchronous authentication service and auth ViewModel/provider to support stored-session restoration, lifecycle updates, recovery, and local sign-out. Continue the MVVM boundary: views render state, services hide Supabase details, and SDK credentials are not exposed to View components.
- Reuse the shared Supabase client and existing persisted-session storage/process lock. Let the SDK manage token renewal; do not create a competing refresh-token store or independent renewal loop. Handle native foreground/background lifecycle and dispose listeners/subscriptions appropriately.
- Represent unresolved restoration separately from signed-out access. Gate protected routes, including direct entry, until usable authentication and application User loading/name onboarding are resolved. Do not briefly render cached training or prematurely show email entry during a valid restoration.
- Restoration reuses the existing application User contract: load the account's User; an absent User requires name onboarding; a failed lookup remains a retryable loading failure. Auth metadata is not the authoritative account name. Do not create an application User merely by restoring credentials.
- Distinguish an expired access token that can be renewed from definitively ended authentication. Retain the ADR's renewable-session intent and impose no maximum lifetime or inactivity timeout.
- Routine same-account background token refresh updates current credentials without resetting drafts, cached training, or navigation. Repeated same-account lifecycle notifications alone must not be treated as account changes.
- When authentication becomes unusable, immediately gate training and prevent protected actions. A temporary network/service failure preserves stored authentication and offers Retry, Sign out, and appearance Settings. Do not require another OTP solely because a retryable service failure occurred.
- Successful recovery after authentication became unusable starts a clean account load: discard unsaved drafts, account edits, account-specific cached data, and prior protected navigation before training reopens. Explain draft loss. This reset also applies if recovery returns the same account. It does not apply to routine token refresh while authentication remains usable.
- Definitive credential invalidation or a signed-out transition clears account-specific state and returns to email entry with an explanation. Classify authentication failure separately from ordinary network, application validation, or permission errors; an arbitrary failed protected request is not proof that the whole authentication session ended.
- Define an account-lifetime boundary around both stateful service instances and their providers/resources. Reset template drafts, mutated sample-service data, list/detail reads, workout history state, account edits, pending-operation state, catalog selections associated with drafts, and protected navigation when authentication ends or identity changes. Unmounting screen components alone is insufficient because the existing root-owned sample service and draft provider survive route changes.
- Invalidate outstanding work at that boundary. Late restoration results, User loads, name updates, training reads/writes, and old auth updates cannot overwrite newer account state or trigger stale navigation. This includes sign-out followed by sign-in to the same account.
- Forced authentication loss takes priority over pending-operation and unsaved-navigation guards. Immediately hide protected content and perform cleanup. A backend request already accepted may still commit; client cleanup does not promise rollback or deletion of saved records.
- Deliberate sign-out is disabled while a save is pending. Otherwise, ask for confirmation only when unsaved changes exist; cancel preserves work and confirmed sign-out discards it. Apply pending controls to prevent duplicate sign-out/recovery actions.
- Sign out only the current device session, explicitly selecting local scope rather than the SDK's global default. Remove local stored credentials and account state and return to email entry even if the best-effort server revocation request fails. Do not claim all devices were signed out, server revocation succeeded on failure, or already issued access tokens were immediately invalidated.
- Local credential-cleanup failure is different from server revocation failure. Keep protected content hidden, show a blocking cleanup error with Retry, and prevent another account from entering until durable local cleanup succeeds. Do not report successful sign-out while stored authentication can still be restored.
- Offer Sign out on Account, name onboarding, and authentication/account recovery screens. Preserve appearance Settings and device appearance preferences across authentication transitions.
- Ordinary restored launch, successful sign-in, and clean recovery open Templates after account readiness. Valid protected direct links wait for authentication and required onboarding. Prior protected navigation is not restored after a clean recovery or account change. Back cannot expose ended account access or the previous account's protected screens.
- Account switching is sign-out followed by the existing email OTP flow. Do not add a multi-account picker.
- Protected service requests use the shared client's current authenticated context, including refreshed credentials. Do not use an account ID or publishable key as proof of user identity, capture a stale UI token for later requests, or introduce privileged credentials into the app. Feature backends must preserve that requesting-user context so ownership policies apply.
- Existing application User operations provide a real protected request path for this issue. Template, workout-session, and maximum persistence/backends remain with #45, #47, and #49; authentication lifecycle work does not require implementing them here.
- No personal exercise maximum state currently exists. Amend the original seeded-maximum acceptance expectation: #43 proves cleanup of existing template/history/draft state and establishes the lifecycle future maximum state must share; concrete maximums cleanup verification belongs to #49. Do not build a maximum model/cache solely for this test.
- No database schema change is required for this specification. Saved backend data survives local cleanup and sign-out. Keep existing email OTP behavior, application User storage, appearance behavior, and supported mobile environments.

## Testing Decisions

- The maintainer approved the existing router-level seam as the primary boundary: mount real screens/navigation with injected authentication and workout services, controlled clocks, and deferred asynchronous results.
- Good tests assert visible content, available actions, navigation, and externally observable service behavior. Avoid tests coupled to hook internals, provider layout, implementation call order, or incidental SDK event counts.
- Extend existing account-access/navigation tests and their controlled service doubles. Existing template draft, pending-save, error/retry, and history navigation tests provide prior art for seeded state and delayed outcomes.
- Cover valid restoration, no stored session, pending restoration without a protected-content or sign-in flash, expired-but-renewable access, definitive invalidation, missing User/name onboarding, and failed User lookup/retry.
- Cover routine same-account refresh preserving draft and navigation; temporary unusable authentication gating training; retry without another OTP; and successful recovery performing a clean load with draft/navigation loss.
- Cover local sign-out with and without unsaved changes, cancel/confirm behavior, deliberate sign-out disabled during pending saves, forced loss overriding pending guards, and sign-out available from onboarding/recovery.
- Cover server revocation failure with successful local sign-out separately from device storage cleanup failure with blocked access and retry. Verify successful cleanup prevents restoration on a subsequent launch.
- Seed distinct existing template/history/draft/account-edit state. Verify sign-out, account change, and signing back into the same account do not resurrect it. Appearance preferences must remain.
- Resolve old account/restoration/name/training operations after sign-out, identity change, or recovery and assert they neither repopulate data nor navigate. Verify Back and protected direct links obey the gate.
- Supplement the primary UI seam with the existing disposable-local-Supabase verification approach. Exercise actual persisted restoration across service recreation, renewal, local sign-out, restart after sign-out, and protected application User requests under two accounts/current credentials. Verify local sign-out leaves a separate device/session usable.
- Feature-specific persistence and actual cross-account database isolation remain tested in their owning tasks. Concrete maximums cleanup belongs to #49.
- During implementation, run the checked-in TypeScript and Jest commands and appropriate native bundle/dependency checks. Device review must cover process restart, foreground/background lifecycle, sign-out/re-entry, protected-content gating, readable recovery controls, and both themes. Physical iPhone with Expo Go is the first review target; Android remains supported. Automated tests and bundles do not replace native review.

## Out of Scope

- Implementing template, workout-session/history, or personal exercise maximum persistence, feature HTTP endpoints, or feature-specific ownership policies.
- Adding a maximum model/cache or maximum screens merely to satisfy cleanup coverage.
- Offline training, offline synchronization, draft persistence, or recovering unsaved work after unusable authentication recovers.
- A multi-account picker, sign-out-all-devices UI, account deletion, sign-in email changes, or new profile fields.
- Passwords, password recovery, OAuth, magic links, authentication callbacks, or changing the agreed email OTP flow.
- New app-imposed session lifetime/inactivity limits, replacement credential storage architecture, or immediate invalidation of already issued access tokens.
- Deleting saved backend training data on sign-out or promising rollback of a request already accepted by the backend.
